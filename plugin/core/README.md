# BloodNight Plugin

`:core`: the Paper plugin itself. It decides which nights are blood nights, turns spawning mobs into custom mobs,
compiles each mob's node graph into Java at runtime, applies the blood night rules, and exchanges its configuration
with the web editor.

## Overview

`de.eldoria.bloodnight.BloodNight` is the entry point. On enable it loads the configuration, writes the default mobs to
`mobs.yml` if the file does not exist, builds the node platform from [bukkit-nodes](../bukkit-nodes/README.md), wires up
listeners and timers, and compiles every mob's behaviour in the background.

- **Behaviours.** `BehaviourService` compiles all mobs on one background thread. Unchanged graphs are restored from a
  bytecode cache on disk, keyed by a hash over the plugin build, the graph and the macro library. A mob whose graph
  does not compile keeps its problems and gets no behaviour; the others are unaffected. Once compiled, living mobs get
  fresh instances of the new classes on the main thread, and `TriggerDispatcher` listens only for triggers some graph
  uses.
- **Custom mobs.** A `CustomMob` (in `mobs.yml`) has an entity type, attributes, equipment, an optional extension
  (an entity riding or carrying it), loot settings, spawn rules and its behaviour graph. `MobSpawner` takes over a naturally
  spawning entity one tick after it spawned when its world is enabled, a custom mob fits by type, spawn rules and
  weight, and the world's spawn chance hits. Each living mob has its own behaviour instance (`MobCoordinator`); mobs
  are tagged in their persistent data and taken over again when their chunk loads.
- **Loot.** Loot tables (`loot_tables.yml`) list entries: an item, a weight, an amount (a range or weighted
  choices) and whether it can drop twice in one kill. The mob, its world and the server assign tables; a kill by a
  player pools the tables of every level the mob inherits, lets a level with `replaceSame` take the same items out of
  broader ones, rolls how many entries drop from the most specific level that sets it, and picks them by weight
  (`LootRoll`, `DropHandler`). Experience follows the most specific level that sets it. Ordinary enemies roll their
  own lists during blood nights. Other plugins can change the rolled loot (`BloodNightLootEvent`). Other deaths keep
  their vanilla drops only.
- **Nights.** `NightSelector` decides each night by its number alone: a roll from a per-world secret salt and the
  night number against the probability of the world's night selection type (random, interval, curve, moon phase, real
  moon phase, custom phases). The answer is stable across restarts and can be asked for in advance. Salt and admin
  overrides live in the world's persistent data container. `BloodNights` begins and ends blood nights and fires the
  events of [api](../api/README.md); `NightStretch` gives them their configured length.
- **Rules.** While a blood night runs: scaled damage, blocked commands, creeper block protection, forced phantoms,
  death actions (lightning, shockwave, item and experience loss, commands, respawn effects), and no sleeping through a
  night that is not skippable.
- **Announcements.** Begin and end messages (chat, title, subtitle or action bar), a boss bar, begin effects, sounds
  and ambience. Texts are MiniMessage in `src/main/resources/messages/<language>.properties` (en, de, es, ms, tr,
  zh), rendered in each player's client language.
- **Editor.** The plugin opens a session on the editor service (see [web/backend](../../web/backend/README.md)), uploads
  the catalog and a payload of mobs, macros, items and settings, and later pulls the result back and applies it.

## Layout

All packages are below `de.eldoria.bloodnight`.

- `BloodNight`: plugin entry point, startup wiring, `recompile()`.
- `announce`: `Announcer`, `Messages` (translations), `Delivery`; `announce.night`: `NightBars` (boss bars),
  `Ambience` (sounds) and `IntroDialog`.
- `atmosphere`: `Haunting`, `Omens`, `ScreenEffect`, `ArmorCalm`; `atmosphere.pack`: `BloodPack` and `PackMerge` (the
  resource pack); `atmosphere.timeline`: `Timelines` and `TimelineGroup` (the data pack timelines).
- `behaviour`: `BehaviourService` (background compiling), `BytecodeCache`, `Behaviours` (result of a compile run).
- `command`: `/bloodnight`, `Replies` and `ReloadCommand`; one subpackage per area (`editor`, `item`, `night`,
  `settings`, `store`, `setup`) with a class per subcommand (StrokkCommands annotations, Brigadier code generated by
  its annotation processor); `command.suggest`: suggestion providers for mob ids and world names.
- `configuration`: `Configuration` (every file, reload, backup, file hashes), `ConfigFile` (`config.yml`),
  `MacroFile`; `configuration.server` holds the server-wide settings classes (`server.plugins` those for other
  plugins), `configuration.world` the settings per world, with `world.presentation` for announcements, sounds and
  atmosphere and one subpackage per further part.
- `editor`: `EditorClient` (HTTP client of the editor service), `EditorResult` (what comes back), `EditorChecks`
  (validation before applying: mob ids, entity types a mob can be, known items, changed files), `EditorSessionFile`;
  `editor.payload`: `EditorPayload` (what goes out), `EditorChoices` (what the server offers to pick from, including
  the mob types); `editor.item`: `EditorItems`; `editor.catalog`: `BundledCatalog` and `RuntimeCatalog`.
- `items`: `ItemRegistry` (items by id: registered from the game under a hash id, or `ItemDefinition`s made in the
  editor; any other id is read as a material key), `ItemTexts`; `items.look`: attributes, slots, trims and tooltip
  parts of a defined item.
- `living`: living mobs: `MobCoordinator`, `MobLifecycle`, `LivingMobContext` (the `MobContext` implementation),
  `MobRegistry` (contents of `mobs.yml`); `living.spawn`: `MobSpawner`, `MobSelector`, `MobOutfitter`,
  `ForeignMobs`; `living.combat`: `TargetPolicy`, `DamageHandler` (damage and death between a mob and its
  extension), `HeldPassengers`, `MobDeaths`; `living.movement`: steering on top of the vanilla AI.
- `loot`: loot tables and their entries; `loot.roll`: `LootRoll`; `loot.assign`: the tables of a mob, a world and
  the server; `loot.drop`: `DropHandler`, `PickupGuard`, `RewardLoot`.
- `mob`: `CustomMob`, `MobTypes` (the entity types a custom mob or its extension can be: spawnable mobs),
  `SpawnReasons`, `MobOrigin`; `mob.attributes`, `mob.spawn` (spawn rules and conditions) and `mob.equipment`
  (equipment and extension); `mob.defaults` (`DefaultMobs`, the shipped mobs, built as graphs with `MobGraph`);
  `mob.serialization` (Jackson serializers for the editor payload).
- `night`: `BloodNights`, `NightStretch`, `NightSkipGuard`, `NightCommands`, `DragonFight`; `night.selection`:
  `NightSelector`, `NightTimes`, `Prediction`.
- `rules`: `WorldRules`, `MobDamage`, `CommandBlocker`, `PhantomForce`; `rules.death`: `DeathActionHandler`,
  `Shockwave`; `rules.explosion`: `CreeperGuard`, `HarmlessExplosions`.
- `store`: `MobStore` and the store entries; `store.files`: the store's files and packs; `store.build`:
  `BuiltInStore`, `StoreGenerator`.
- `util`: `MobTags` (persistent data keys on entities), `Effects`.

## Configuration

Files live in the plugin's data folder (`plugins/BloodNight/`). There are two kinds:

- **Settings files** are completed on load: once read they are written back, so options added by a newer version
  appear with their defaults.
  - `config.yml`: server-wide announcements (prefix, reach, method, fallback language), the editor service
    (`url`, `timeoutSeconds`) and the server's loot.
  - `worlds/<world UID>.yml`: everything per world: `enabled`, night selection, night times, length, commands and
    blocked commands, mob settings and spawning, announcements, sounds, death actions, the world's loot. Created the first
    time the world's settings are read.
- **User data files** are never completed or rewritten on load. One that cannot be read is reported, treated as empty
  and left untouched until it reads again on a later reload.
  - `mobs.yml`: the custom mobs; written with the default mobs on first start only.
  - `items.yml`: the item registry.
  - `macros.yml`: the macro library shared by all mobs.
  - `loot_tables.yml`: the loot tables by id.

The plugin also writes `cache/` (compiled behaviours), `debug/` (output of `source` and `export`),
`editor-session.json` (the open editor session, so it survives a restart) and `backups/<time>/` (copies of every file
above, taken before an editor result is applied).

Configuration classes use non-final fields with inline defaults: Jackson 3 does not write final fields, so a final
field would never be read from the file.

## Commands and permissions

`/bloodnight` (alias `/bn`). Every subcommand needs `bloodnight.command.<subcommand>`; `bloodnight.admin` grants all of
them. All permissions default to operators.

| Command | Does |
|---|---|
| `reload` | Reads the configuration again and recompiles every mob |
| `spawn <mob>` | Spawns a custom mob where the player stands (console: spawn of the first world) |
| `problems [mob]` | Lists compile problems and runtime failures, of all mobs or one |
| `source <mob>` | Writes the generated Java source to `debug/<mob>.java` |
| `debug [mob]` | Fires the debug trigger on every mob, or the mobs of one id |
| `export` | Writes the editor payload and catalog to `debug/` |
| `night [world]` | Shows the world's night selection and next blood night |
| `night force\|cancel [world]` | Forces or cancels the coming night; needs `bloodnight.command.night.manage` |
| `editor` | Opens an editor session, or joins the open one with a personal link |
| `editor new` | Replaces the open session with a fresh one |
| `editor apply [force]` | Pulls the session and applies it |
| `editor cancel` | Closes the session without applying |
| `item register` | Registers the item in the player's main hand under a generated id, shown and copyable |
| `item remove <id>` | Forgets a registered item |

Applying an editor session is the only step that changes files. The result is checked first (mob ids, item
references, and that no file it replaces changed since the session opened; `force` skips that last check). If it
passes, every file is backed up, mobs, macros, items and settings are replaced, and the plugin reloads and recompiles.
Settings of worlds the server does not know are skipped.

`bloodnight.bypass.commands` lets a player use commands that are blocked during blood nights.

## Dependencies

Depends on: [api](../api/README.md), [web/api](../../web/api/README.md), [bukkit-nodes](../bukkit-nodes/README.md) and
[graph-editor-payload](../../graph/editor-payload/README.md); Eldoria utilities, Jackson 3 with jackson-bukkit, Ocular
(configuration files), StrokkCommands (annotation processor). The generated catalog of
[catalog](../catalog/README.md) is bundled as `/catalog.json`. Tests also use
[tools/json-schema](../../tools/json-schema/README.md) and MockBukkit.

Used by: no other module; it is the deliverable. The shadow jar relocates its libraries below
`de.eldoria.bloodnight.libs`.

## Building and testing

```sh
./toolchain.sh be-jar                          # plugin jar into plugin/core/build/libs
./toolchain.sh be-server                       # Paper 26.3 test server in plugin/core/run with the plugin
./toolchain.sh be-test1 core '*Configuration*' # tests matching a pattern
./toolchain.sh be-format                       # formatting and license headers
./toolchain.sh api-types                       # regenerate the payload schema and the frontend types
```

`./gradlew :core:generatePayloadSchema` writes `web/frontend/src/api/generated/payload.schema.json` from the payload
classes. `PayloadSchemaTest` fails while the committed schema is stale, so run `api-types` after changing a record or
settings class the editor sees.

Tests use MockBukkit. Its unimplemented methods throw an exception JUnit reports as a skip, and the build fails on any
skipped test, so a test touching such a method has to avoid it or provide the behaviour itself.
